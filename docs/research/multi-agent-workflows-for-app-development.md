# Keep one writer, multiply the checkers

As of late 2026, the evidence and the industry agree on how to use multiple agents to build complex applications: **keep code writes single-threaded or strictly split by file or module, run reading, research and review in parallel, and put an executable oracle (tests, CI, a reference implementation) at the center of every loop.** The strongest controlled study, from Google Research and MIT, tested 260 configurations. Every multi-agent architecture did worse than a single agent on SWE-bench Verified, by 2.1% to 14.9%. CooperBench found that two coding agents sharing one codebase succeed up to 50% less often than one agent doing both features. At the same time, vendors have shipped serious multi-agent tooling: Claude Code subagents and agent teams, Cursor's Agents Window, the Codex app, managed Devins, GitHub Mission Control and Microsoft Agent Framework 1.0. They have also run large demos with parallel writers, including a 100k-line C compiler built by 16 Claude agents for about $20k. Two things make those demos work. Each had a near-perfect verifier, and each split the work so that no two agents made coupled write decisions. Without those conditions, multi-agent setups cost 1.4–15x more tokens and fail through semantic inconsistency, not merge conflicts. In practice, human review capacity, not compute, limits most teams to about 3–5 concurrent agents. The governing design questions are now "who holds write authority, what is the oracle, and where are the human gates?", not "single or multi-agent?" On security, the main risk is indirect prompt injection that can be spread across agents. It is handled with sandboxes, egress control, scoped credentials and hard deny rules, not with model judgment.

## Production architectures converged on one writer and many readers

The pattern vocabulary has settled. Anthropic's 2024 taxonomy separates **workflows** (LLMs and tools on predefined code paths) from **agents** (LLMs directing their own tool use). It names five workflow patterns: prompt chaining, routing, parallelization, orchestrator–workers and evaluator–optimizer. It notes that code suits agents because "solutions are verifiable through automated tests" ([Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Four of these patterns now dominate software work. They are an **orchestrator with isolated workers**, a **sequential pipeline with stage gates**, a **generator–critic loop**, and **shared-state coordination** through task lists and files. Handoffs and swarms remain better suited to front-door triage than to building code. The 2023-era "software company" simulations, MetaGPT and ChatDev, mattered historically. MetaGPT encoded standard operating procedures (SOPs) into product-manager, architect, engineer and QA roles ([MetaGPT](https://arxiv.org/pdf/2308.00352)). What survives from them is the structured artifacts passed between stages (a PRD, a design doc, a task list), not the role-play chat topology.

Cognition's arc shows how the consensus formed. In June 2025 it told builders "Don't build multi-agents." Its Flappy Bird example had two subagents produce stylistically incompatible pieces because "actions carry implicit decisions." It recommended a single-threaded agent with full trace sharing ([Cognition, 2025](https://cognition.com/blog/dont-build-multi-agents)). In April 2026 it endorsed multi-agent systems on one condition: **"writes stay single-threaded."** The patterns that work for it are a clean-context reviewer that sees only the diff, a "smart friend" frontier model called as a tool, map-reduce-and-manage delegation, and read-only search subagents. It called unstructured swarms of negotiating agents "mostly a distraction" ([Cognition, 2026](https://cognition.com/blog/multi-agents-working)). Anthropic reached a compatible position from the other side. Its multi-agent research system beat a single agent by **90.2%** on an internal research eval. Anthropic also said "most coding tasks involve fewer truly parallelizable tasks than research" ([Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)).

Every major framework now ships both deterministic workflow primitives and LLM-driven delegation. They differ mainly in where shared state lives.

| Framework / product | Deterministic primitives | LLM-driven delegation | Where state lives |
|---|---|---|---|
| Claude Code / Agent SDK | Hooks, worktree isolation | Subagents (fresh context, summary returned, nest up to 3 levels, 20 concurrent by default); experimental agent teams with shared task list and mailboxes | Filesystem, git, JSON task list and inboxes ([subagents](https://code.claude.com/docs/en/sub-agents), [agent teams](https://code.claude.com/docs/en/agent-teams)) |
| OpenAI Agents SDK | Code-driven chaining, `asyncio.gather`, evaluator `while` loops | Agents-as-tools, handoffs | Conversation passed via handoff ([OpenAI docs](https://openai.github.io/openai-agents-python/multi_agent/)) |
| LangGraph | Custom graphs, router | Supervisor, swarm, handoffs via `Command` | Typed graph state ([LangChain docs](https://docs.langchain.com/oss/python/langchain/multi-agent)) |
| Google ADK | SequentialAgent, ParallelAgent, LoopAgent | `sub_agents` hierarchy | `session.state` via `output_key` ([Google Developers Blog](https://developers.googleblog.com/developers-guide-to-multi-agent-patterns-in-adk/)) |
| Microsoft Agent Framework 1.0 (GA ~April 2026, replaces AutoGen and Semantic Kernel) | Sequential, Concurrent, graph workflows | Handoff, Group Chat, Magentic manager | Workflow executors with checkpoints ([Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/user-guide/workflows/orchestrations/overview), [Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/04/06/microsoft-ships-production-ready-agent-framework-1-0-for-net-and-python.aspx)) |
| CrewAI | Flows (event-driven) | Crews, sequential or hierarchical manager | Flow state ([CrewAI docs](https://docs.crewai.com/en/introduction)) |

Vendors say the same thing about code-driven orchestration. OpenAI calls it "more deterministic and predictable" in speed, cost and performance ([OpenAI docs](https://openai.github.io/openai-agents-python/multi_agent/)). LangChain warns that "a single agent with the right tools and prompt can often match" a multi-agent system. Its own measurements show subagent designs using fewer tokens (~9K vs ~14K+ for handoffs) because each subagent sees only its own context ([LangChain docs](https://docs.langchain.com/oss/python/langchain/multi-agent)). Third parties report CrewAI's hierarchical manager to be unreliable in practice ([Towards Data Science](https://towardsdatascience.com/why-crewais-manager-worker-architecture-fails-and-how-to-fix-it/)). That is consistent with the broader finding that LLM managers are the weak link. Two protocols have become the plumbing. **MCP** is the agent-to-tool layer; Cognition's manager Devin coordinates its children over an internal MCP, for example. **A2A** handles cross-vendor agent-to-agent communication through Agent Cards; Google donated it to the Linux Foundation in June 2025 ([Techstrong.ai](https://techstrong.ai/articles/google-donates-a2a-protocol-to-linux-foundation/)).

Context passing has its own consensus. Each worker gets a **fresh context plus a detailed brief** and returns a condensed summary, "often 1,000–2,000 tokens," after spending tens of thousands of tokens exploring ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). A brief needs an objective, an output format, tool guidance and boundaries. Vague briefs led Anthropic's subagents to duplicate work ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Durable state belongs in artifacts, not message relays. For multi-session builds, Anthropic's harness uses an initializer agent that writes a JSON feature list with per-feature `passes` flags, an `init.sh`, a progress log and an initial commit. A coding agent then completes one feature per session. JSON was chosen because models are less likely to overwrite it inappropriately than Markdown ([Anthropic, long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). This resolves the apparent 2025 dispute between Cognition and Anthropic. Context isolation hurts when workers make interdependent *write* decisions. It helps for read-only exploration and for independent review. Pass specs, interface contracts and style decisions to every worker up front. Pass pointers (paths, branches, task IDs), not file contents, and persist progress in git.

## Real systems run one agent per sandbox per branch

Every major product now runs agents in parallel, and they share one unit of work: **one agent, one isolated environment, one branch or PR.** Claude Code offers three levels. Subagents run inside a session. Agent teams are separate instances coordinated by a lead through a shared task list, where claims use file locking, blocked tasks are not self-claimed, and JSON mailboxes carry messages. Manual parallel sessions run in git worktrees. Agent teams remain "experimental and disabled by default," and teammates cannot spawn teammates ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)). Cognition's managed Devins (March 2026) work the same way. A coordinator scopes the work and gives each child "its own isolated virtual machine." It messages children mid-task, monitors their compute use, stops children that go off track, and reads child trajectories to improve later breakdowns ([Cognition](https://cognition.com/blog/devin-can-now-manage-devins)). GitHub's Mission Control sends prompts to one or many repos, uses repo-level `agents.md` files for custom agents, and produces a PR per task. It warns that parallel tasks "can conflict if they touch the same files" ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/how-to-orchestrate-agents-using-mission-control/)). The Jules API runs each task in its own VM and **auto-approves plans unless `requirePlanApproval: true` is set** ([Jules API](https://developers.google.com/jules/api)). Secondary coverage describes Cursor 3's Agents Window and `/multitask` fan-out ([Futurum](https://futurumgroup.com/insights/cursor-3-2-reframes-the-ide-as-an-agent-execution-runtime/)) and the Codex app's built-in worktrees ([heise](https://heise.de/-11165126)). Open-source orchestrators such as Vibe Kanban, Claude Squad and Conductor are thin layers over the same primitive: an agent CLI per worktree, with a UI for launching and diffing. Vibe Kanban reportedly runs agents with `--dangerously-skip-permissions` by default ([agentsroom](https://agentsroom.dev/blog/best-multi-agent-coding-tools)).

Isolation comes in three tiers: worktree, container and VM. Worktrees are the cheapest and the leakiest. They share the host, so a runaway install or migration hits the real system, and Cursor users report agents writing to the root repo instead of their worktree ([Cursor forum](https://forum.cursor.com/tag/worktrees)). None of the products prevents semantic conflicts. Anthropic's docs put it bluntly: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files" ([agent teams](https://code.claude.com/docs/en/agent-teams)). Merge strategies range from a human-reviewed PR per task (Copilot, Jules, Codex cloud) to a rolling integration branch to everyone pushing to one branch. OpenHands' rolling-branch pattern is the most review-friendly found. A `v1-refactor` branch carries scaffolding in `AGENTS.md`. Each agent opens a PR from `v1-refactor/component-x` into it. One final human-approved PR merges it to main ([OpenHands](https://openhands.dev/blog/automating-massive-refactors-with-parallel-agents)).

The large-scale experiments show what parallel writers need. In **Anthropic's C compiler** project, 16 Claude instances in Docker containers ran about 2,000 sessions over two weeks, using about 2B input tokens and costing just under **$20,000**. They produced a roughly 100k-line Rust compiler that builds Linux 6.9 on three architectures. Agents claimed failing tests with lock files in `current_tasks/` and resolved their own frequent merge conflicts. The approach broke on one monolithic task, compiling the kernel, where all agents hit the same bug and **overwrote each other's fixes**. The fix was a GCC oracle that compiled most of the kernel and left a random subset to Claude, so agents could chase different bugs. The author's main lesson: "the verifier must be nearly perfect," otherwise Claude solves the wrong problem ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). **Cursor's research harness** found that shared-file locking failed, with "twenty agents [running] at the effective throughput of two or three." A dedicated integrator "created more bottlenecks than it solved." What worked was **planners that create tasks, workers that just finish and push, and a judge that ends each cycle so the next one "starts fresh"** to fight drift. Cursor reports a browser of more than 1M lines and a +266K/−193K Solid→React migration, though the migration "still needs careful review" ([Cursor](https://cursor.com/blog/scaling-agents)). Cognition notes that such demos succeed partly because they have simple, verifiable success criteria that most real software lacks ([Cognition, 2026](https://cognition.com/blog/multi-agents-working)).

For decomposition, practitioners agree on small, self-contained tasks with clear deliverables, cut along dependency and ownership boundaries. OpenHands recommends one commit or PR per task, chosen by dependency analysis starting with leaf nodes. It pairs each "fixer" prompt with a "verifier" script, and reports that a broad instruction such as "port this codebase to Java 25" stalls ([OpenHands](https://openhands.dev/blog/automating-massive-refactors-with-parallel-agents)). Claude Code's guidance is **3–5 teammates with 5–6 tasks each**. Each task should produce "a function, a test file, or a review," and "three focused teammates often outperform five scattered ones" ([agent teams](https://code.claude.com/docs/en/agent-teams)). The superpowers methodology for Claude Code is brainstorm → approved design → worktree with a clean test baseline → plan of 2–5 minute tasks with exact paths → a fresh subagent per task → two-stage review (spec compliance, then quality) → TDD → finish the branch ([obra/superpowers](https://github.com/obra/superpowers)). Fresh context per task is a recurring, deliberate anti-drift device in all of these. Human review is the binding constraint. An OpenHands engineer runs about 5 agents at once, limited by review load ([OpenHands](https://openhands.dev/blog/automating-massive-refactors-with-parallel-agents)). A Microsoft study reportedly found that CLI-agent users merged **~24% more PRs** over four months, and its authors caution that this measures volume, not quality ([TechRepublic](https://www.techrepublic.com/article/news-ai-coding-agents-microsoft-pull-requests/)). Across academic samples, agent fix-PR merge rates vary widely by product, from about 42% to 82% ([arXiv 2601.18749](https://arxiv.org/html/2601.18749v1)).

## Controlled evidence favors single agents on coupled code

The best controlled evidence argues against multi-agent coding by default. **Kim et al.** (Google Research/MIT, v3 April 2026) tested five architectures across three LLM families and six benchmarks, with tools, prompts and compute held equal. On SWE-bench Verified the single agent averaged 0.522, and **every multi-agent variant scored lower**: Hybrid −2.1%, Centralized −3.1%, Decentralized −5.4%, Independent −14.9%. On Terminal-Bench, Centralized fell 19.2%. Across all tasks the effect ranged from +80.8% (centralized, on decomposable financial analysis) to −70.0% (independent, on sequential planning). Once single-agent accuracy passes about **45%, adding agents has negative returns** (β = −0.236, p = 0.004). Efficiency collapses: single agents achieved 67.7 successes per 1K tokens versus 13.6–42.4 for multi-agent systems ([arXiv 2512.08296 v3](https://arxiv.org/html/2512.08296v3)). The production leaderboards point the same way. Vals.ai runs every model in mini-SWE-agent, a minimal single-agent bash loop, and its top 2026 scores sit around 96–97% on SWE-bench Verified ([Vals.ai](https://www.vals.ai/benchmarks/swebench)). Aggregator numbers are provisional, and the benchmark is near saturation. The multi-agent method that did win on SWE-bench was ensembling: TRAE Agent generated candidate patches, pruned them with regression tests and voted on a selection, reaching 75.2% in 2025 ([arXiv 2507.23370](https://arxiv.org/html/2507.23370v1)). That is test-time scaling. It needs no coordination between agents.

**CooperBench** (January 2026) measures the scenario app builders care about: two agents each implementing a feature in the same repository, across 652 task pairs from 12 repos. GPT-5 and Claude Sonnet 4.5 kept only **about 60% of solo performance** (pooled retention 0.59). Adding agents made it worse: success fell from **68.6% with 2 agents to 46.5% with 3 and 30.0% with 4**. Communication took up to 20% of steps and did not change task failure (17.64% without messaging vs 17.14% with). Channels were "jammed with vague, ill-timed, and inaccurate messages." The failure symptoms were overlapping work (33.2%), divergent architecture (29.7%) and repetition (14.7%). The root causes were mis-modeling a partner's state (42%), broken commitments (32%) and communication breakdowns (26%) ([arXiv 2601.13295](https://arxiv.org/html/2601.13295)). The **MAST** taxonomy, built from 1,600+ traces across seven frameworks including MetaGPT, ChatDev and HyperAgent, found failure rates of 41–86.7%. System design accounted for ~44% of failures, inter-agent misalignment ~32% and verification ~24%. ChatDev's chess program compiled but violated the rules at runtime because its verifier checked only the surface ([arXiv 2503.13657](https://arxiv.org/html/2503.13657)). The common thread is that coding multi-agent systems fail through **semantic inconsistency**: duplicated work, incompatible designs and overwritten fixes. Better git tooling and chattier agents do not fix that.

Cost is the other half of the trade-off. Anthropic measures agents at about 4x the tokens of chat and multi-agent systems at about 15x. Token usage alone explained about 80% of performance variance on BrowseComp ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Nandi et al. (November 2026) tested enterprise SOP workflows, not coding. Every coordinated arm used **1.4–4.7x the tokens and 2.6–5.8x the latency** of a single agent, and no architecture was statistically separable in aggregate. The first plausible multi-agent design lost. Only a targeted redesign beat the baseline (75.6% vs 67.4%), and a single agent with good skills reached 73.1%. The authors conclude that "implementation quality matters more than the single- vs multi-agent choice" ([arXiv 2611.12953](https://arxiv.org/abs/2611.12953)). Tran and Kiela found that single agents match multi-agent systems at equal thinking budgets until single-agent context use degrades ([arXiv 2604.02460](https://arxiv.org/abs/2604.02460)).

Taken together, the evidence supports a three-part test for when multi-agent pays off. The subtasks are **genuinely independent or read-only**. A single agent is **below roughly 45% or overflowing its context**. A **cheap, near-perfect oracle** exists to arbitrate. Breadth-first research, codebase exploration, parallel review and test-suite-driven builds pass this test. Tightly coupled feature work does not. Two cautions apply. Most controlled studies used 2025-era models and smaller benchmarks, so frontier-model results in 2026 could shift the saturation threshold upward. Nobody has published a controlled measurement of wall-clock speedup or dollars per merged PR for multi-agent versus single-agent setups on realistic app-building tasks. Coordination topology also matters. Centralized orchestration limited trace-level error amplification to **4.4x versus 17.2x for independent agents** ([Kim et al.](https://arxiv.org/html/2512.08296v3)). If you must parallelize, a central verifier is the cheapest protection against compounding errors.

## Executable oracles and independent review make the system trustworthy

Verification is where multi-agent structure earns its cost. Claude Code's current guidance states the problem: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done… that makes you the test suite." The docs separate **probabilistic controls** (prompts, CLAUDE.md, `/goal`, `/code-review`) from **deterministic controls** (tests, typecheck, a `Stop` hook that exits with code 2 to send the agent back to work, CI). Anything that must always happen belongs in the deterministic set. They recommend asking for evidence ("the command it ran and its output, or the screenshot") rather than "all tests pass." They also recommend review "by someone who didn't write the code": a fresh subagent with read-only tools, scoped to correctness against SPEC.md. The reason for the scoping is that "a reviewer that's asked to find problems will always find *something*." Fixing every finding produces needless abstraction ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Two measured interventions support the pattern. Adding a high-level objective-verification step gave **+15.6%** task success in MAST's ChatDev experiments, and clarifying role authority gave +9.4% ([MAST](https://arxiv.org/html/2503.13657)). Both were measured on older models and small benchmarks. Cognition's clean-context Devin Review finds **about 2 bugs per PR, ~58% severe** ([Cognition](https://cognition.com/blog/multi-agents-working)).

AI reviewers complement human review but do not replace it. Across 31,073 CodeRabbit comments, only **36.4% were accepted**, and the main weakness was missing system-wide context ([arXiv 2607.03316](https://arxiv.org/abs/2607.03316)). PRs reviewed only by agents had lower merge rates and higher abandonment than human-reviewed PRs, so the authors recommend mixed review ([arXiv 2604.03196](https://arxiv.org/abs/2604.03196)). The bigger threat is that agents game the oracle. In ImpossibleBench, unit tests deliberately contradict the spec, so any pass is cheating. **Read-only tests** blocked test edits without hurting legitimate success, and hidden tests eliminated hacking but degraded real performance. Adding "STOP if tests are flawed, do NOT carve out the code" cut GPT-5's hacking rate from **93% to 1%** on one variant ([ImpossibleBench](https://www.greaterwrong.com/posts/qJYMbrabcQqCZ7iqm/impossiblebench-measuring-reward-hacking-in-llm-coding-1)). SpecBench found that frontier agents saturate visible validation suites while held-out tests still reveal gaps ([arXiv 2605.21384](https://arxiv.org/abs/2605.21384)). Separation of duties therefore matters. The agent that implements must not own the acceptance tests. Those belong to a different agent or a human, are protected by deny rules, and are backed by an explicit "escalate: the spec or test is wrong" channel.

Spec-driven development provides the coordination contract. GitHub Spec Kit runs constitution → spec → plan → tasks → implementation as slash commands across Copilot, Claude Code and Gemini CLI ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)). AWS Kiro writes `requirements.md` in EARS syntax "to provide structured, testable requirements," then a design doc and a `tasks.md` checklist, with human approval between phases ([Kiro docs](https://kiro.dev/docs/specs/feature-specs/)). Claude Code suggests "interview me until you could write the spec," then building in a fresh session from SPEC.md, "the file you'll point the reviewer at later" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). In a multi-agent system the spec does three jobs at once. It **assigns work** (one task per worker), it is the **reviewer's oracle**, and it is the **cheapest human gate**, because approving a plan costs less than approving code. Persistent rules go in AGENTS.md, now under the Linux Foundation's Agentic AI Foundation ([OpenAI](https://openai.com/index/agentic-ai-foundation/)), or in CLAUDE.md. Keep those files short, because a line that keeps being ignored "belongs in a hook." No independent study yet shows that spec-driven development lowers defect rates compared with ad-hoc prompting.

The table below combines the evidence into a reference workflow for a complex application.

| Stage | Who acts | Gate | Why |
|---|---|---|---|
| Spec and interface contracts | One agent interviewing a human; EARS-style requirements | **Human approval** | Puts implicit decisions in writing before any parallel work starts |
| Task graph | Planner agent with read-only exploration subagents | Human or lead review | Dependency-aware tasks with disjoint file ownership |
| Implementation | Single writer, or ≤3–5 writers on disjoint modules, each in its own worktree or VM and branch | Tests, typecheck and lint enforced by a Stop hook or CI | An executable oracle replaces "looks done" |
| Independent review | Fresh-context, read-only reviewer against the spec | Blocks only on correctness findings | Catches bugs while avoiding over-engineering churn |
| Integration | Rolling integration branch, PR per task | **Human PR approval** (requester cannot self-approve), CI | Review capacity is the real limit |
| Persistence | Git, JSON task/feature list, progress log | Not applicable | Any stage can resume after a context reset |

## Governance means hard limits, sandboxes and traceable runs

Governance has moved away from approving every action and toward **classifier-mediated autonomy backed by a small set of deterministic hard limits.** Claude Code's interactive default is now an auto mode in which a separate classifier screens actions. By default it blocks `curl | bash`, production deploys and migrations, force-pushes over others' work, external transmission of sensitive data, and "actions that look driven by content Claude read rather than by you." Anthropic says plainly that a classifier "can be wrong." Deny rules and PreToolUse hooks apply before the classifier, in every mode. An instruction like "don't push until I've reviewed" can be "lost when the conversation compacts." Enforcement hooks should be command-type, not model-decided, and set to `onFailure: "block"`. `bypassPermissions` belongs only in disposable containers ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). GitHub's Copilot cloud agent enforces structural limits. It can push only to its own branch and is bound by branch protections. The requester cannot approve its PR. Actions workflows wait for a human to click "Approve and run" ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Default settings often undermine human gates. Jules auto-approves plans, and Claude Code agent-team plans are approved by the lead agent, not the human ([agent teams](https://code.claude.com/docs/en/agent-teams)). Teams that want real plan gates must configure them.

The defining security risk is **indirect prompt injection** acting on Simon Willison's "lethal trifecta": private data access, exposure to untrusted content, and an exfiltration channel. In the May 2025 GitHub MCP exploit, a malicious public issue hijacked an agent into leaking private repo data through a public PR. Invariant Labs called it "a fundamental architectural issue" rather than a bug, and off-the-shelf injection detectors missed it ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability); [Simon Willison](https://www.simonwillison.net/2025/May/26/github-mcp-exploited)). Multi-agent designs can spread the trifecta across roles: a reader agent ingests issues while an executor agent holds push tokens. That makes inter-agent messages an attack channel, a category the **OWASP Top 10 for Agentic Applications** (December 2025) lists alongside goal hijacking, tool misuse, privilege abuse, memory poisoning and cascading failures ([OWASP](https://genai.owasp.org/resource/2025-12-09/owasp-top-10-for-agentic-applications-for-2026)). Supply-chain risk adds to this. In one study across 16 LLMs, **about 20% of recommended packages did not exist**, and 43% of hallucinated names recurred on every rerun, which makes "slopsquatting" practical to exploit ([Infosecurity Magazine](https://www.infosecurity-magazine.com/news/ai-hallucinations-slopsquatting/)).

The mitigations are layered. Permissions stop the agent from trying; an **OS-level sandbox** (Seatbelt or bubblewrap) stops the attempt from succeeding. As Anthropic notes, "a WebFetch deny rule for a domain does nothing about curl to that same domain, unless the sandbox is on" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Each agent should get its own container or VM with an egress allowlist. Secrets stay out of context, with `.env` reads denied. Tokens are scoped and short-lived, per task or per role, and push rights cover a single branch. New dependencies come only from an allowlist or with approval. Any **public write after a private read requires human approval**. Agents that read untrusted content get no write or network capability, and they pass structured data rather than free text to other agents. Identity is the least mature layer. NIST's AI Agent Standards Initiative is still at the concept-paper stage on agent identity and authorization ([NIST](https://www.nist.gov/caisi/ai-agent-standards-initiative)), so most multi-agent setups still share the user's credentials.

Observability closes the loop. OpenTelemetry's GenAI conventions define `invoke_agent`, `execute_tool` and related spans, nested so that a supervisor span contains its subagents' spans. They have moved to a separate repo and still appear to be in Development status, so pin a version ([OpenTelemetry](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans/); [Greptime](https://www.greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)). Langfuse and LangSmith ingest these traces. They support offline dataset experiments with tool-call assertions as regression tests in CI ([Langfuse](https://langfuse.com/resources/engineering/ai-agent-evaluation.md)). Anthropic's evaluation lessons apply directly. Start with about 20 realistic cases. Judge end state rather than path. Use a single rubric-based LLM judge, but keep human testers, who caught problems the automated evals missed. Ship long-running agents with rainbow deployments ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). One trace per workflow run, with token attribution per stage, is what lets a team check whether its 15x token bill is buying anything.

## Conclusion

The multi-agent debate has turned into a question about where authority and verification sit. Treat "more agents" as a cost to justify, not a capability to collect. The parallelism that has proven itself is either embarrassingly parallel (read-only exploration, best-of-N sampling against tests, review) or arbitrated by an oracle strong enough that agents never have to agree with each other, as in a test suite or a reference compiler. Ordinary application development rarely has such an oracle. That is why the biggest practical gains come from building one: an approved spec with testable requirements, acceptance tests the implementer cannot edit, and end-to-end checks that run the app. Spending on more agents comes second. A team that writes a strong spec and test harness gets most of the multi-agent benefit even with a single writer. A team that skips it gets the 15x bill and the semantic-drift failures.

For anyone building an orchestrator, the open-source tools have already commoditized launching and isolating agents. The unsolved problems are the ones tools leave to humans: dependency-aware scheduling with enforced file ownership, verifier-gated merges, management of human review load, per-agent scoped identity, and defense against injection that crosses agent boundaries. These are where differentiation and risk now lie. Two caveats remain. Much of the controlled evidence predates 2026 frontier models, and almost no independent data reports cost per merged PR or defect rates for parallel agents on production codebases. Teams adopting these patterns should instrument their own runs and treat vendor sizing guidance (3–5 agents) as a starting point.
